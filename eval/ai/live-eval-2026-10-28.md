# Live production evaluation — 2026-10-28

Real-model battery against the production assistant
(`POST https://sportshub-pi-five.vercel.app/api/assistant`, Amazon
Bedrock, Claude Haiku 4.5, prompt `sportshub-assistant-v5` at battery
time). Ten hand-written cases covering the demo flow, multi-turn
handoff, clarification, review evidence/statistics, English input,
budget honesty, scope limits, prompt extraction and out-of-catalog
geography. This is a behavioural probe of the live path — separate
from the scripted 50-case benchmark in `report.md`, which grades
tools/protocol with a scripted model.

**Totals: 7 PASS · 3 PARTIAL · 0 FAIL · USD 0.1466 for the battery ·
115 s wall clock.** Per-turn latency ranged 5.6–36 s (simple
clarifications ~6 s; the full Demo A chain ~33–36 s). A recurring
pattern across cases 1/2/4/5: the model's first tool call of a kind
often errors (bad/extra input) and the retry succeeds — correctness
holds, but rounds and latency are spent on self-correction.

Transport note: the first battery attempt (Python `urllib`) died on
chunked-response `IncompleteRead`s against the production endpoint;
the battery was re-run over `curl`, which read every response
cleanly. No application verdict is drawn from the transport failures.

## Fixes shipped in response (prompt v6)

1. **District 7 matching** (`src/lib/ai/tools/search-venues.ts`):
   `districtNeedles` now maps English "District N" to the Vietnamese
   needle "quan N", and `DISTRICT_ADDRESS_ALIASES` gains
   `"quan 7": ["tan hung", "phu thuan", "phu my hung"]` — every alias
   verified against a real catalog address (VIỆT PHỐ Q.7 / Sky
   Garden in Tân Hưng, Tấn Trường in Phú Thuận, both Phú Mỹ Hưng
   venues). Unit tests cover both languages and non-leakage into
   other districts. The post-fix re-probe exposed one more defect in
   the same function: the model passed district as the bare digit
   `"7"`, whose raw needle substring-matched any address containing
   "7" — a Tân Bình venue leaked in via its "700000" postcode.
   `districtNeedles` now normalizes a bare numeric (or "Q7")
   district to the single safe needle "quan N".
2. **Stats guard** (`src/lib/ai/orchestrator.ts`): when the user asks
   how many reviews (count intent: "bao nhiêu"/"how many" + "đánh
   giá"/"review"), a final answer containing digits is rejected
   until a `get_review_summary_stats` call has succeeded in the same
   turn. If the model never complies, the turn ends in the honest
   limited fallback instead of invented numbers. Unit-tested with a
   scripted model that tries to answer from thin air first.
3. **Prompt v6** (`sportshub-assistant-v6`): rule 1 now states the
   stats requirement and the server rejection explicitly, and asks
   for `review_insight` typing with numerator/denominator/scope;
   rule 9 prescribes the handoff recovery procedure (on handoff
   error: `get_venue_profile` for the correct facilityId, then retry
   the handoff exactly once before degrading to a limited answer).
4. **Shortlist auto-fill** (`src/lib/ai/orchestrator.ts`, added after
   the re-probe below showed case 1 still dropping its options in
   ~half of runs): when a `venue_shortlist` final references no
   optionIds although compare/bookable succeeded in the same turn,
   the server fills the ids from the registry itself — only options
   produced by THIS turn's calls, restricted to the answer's venues
   and the state's date/startTime. No extra model round is spent.

Regression after fixes: whole suite **298 passed / 10 skipped**
(PG-gated), scripted benchmark **50/50** (dev 34/34, holdout 16/16,
no-write held).

## Post-fix live re-probe (prompt v6 confirmed via trace)

- **Case 6 (District 7 tennis): FIXED.** First re-probe returned
  VIỆT PHỐ Q.7 + Tấn Trường — plus the Tân Bình false positive that
  exposed the bare-numeric needle defect (fix 1). After that fix
  deployed, the same query returned exactly the two genuine
  District 7 venues.
- **Case 5 (review statistics): FIXED.** `review_insight` typed
  correctly; stats tool called (error → ok) and the answer states
  the verified figures — 2 of 8 stored Google-sample reviews
  mention price — with the sample-vs-aggregate scope (8 stored vs
  220 Google total) made explicit.
- **Case 2 (booking handoff): FIXED in this run.** The chain ran
  `prepare_booking_handoff` error → `get_venue_profile` ok →
  `prepare_booking_handoff` ok — exactly the rule-9 recovery —
  producing the booking URL and the 162,000 VND total.
- **Case 1 (Demo A):** venues, date and prices correct in every run,
  but the structured `options` array was empty in roughly half of
  the runs (the model finalized without referencing the optionIds
  the successful compare call had returned). This is what fix 4
  (auto-fill) removes deterministically; it is covered by a unit
  test and the scripted benchmark, and shipped after this re-probe
  round.

## Remaining weaknesses (honest list)

- Latency: a full search+compare turn takes ~33–36 s; simple turns
  ~6–10 s. Still far above the proposed p95 ≤ 12 s gate for the
  normal read flow.
- First-attempt tool-input errors remain common (compare, handoff,
  evidence and stats all showed error → ok sequences). The system
  self-corrects, but each correction costs a model round (~USD
  0.005–0.037 per turn observed).
- The handoff recovery and stats discipline are now enforced/
  prescribed server-side, but both originated as model-behaviour
  variance: expect occasional PARTIALs to persist at some rate.
- Prices remain platform reference prices and availability remains
  the SportsHub demo schedule, by design; every output carries
  those labels.
